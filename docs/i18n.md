# Internationalization

Ferum Board serves the public and member-facing UI in the visitor's language. Locale
catalogs are [Fluent](https://projectfluent.org/) `.ftl` files on disk; a separate Tera
instance is built per installed locale, so `{{ t(k="…") }}` resolves in the request's
locale with no per-render lookup.

Two locales ship today: `en` and `vi`. Text direction support is **LTR only** — there
is no Bootstrap RTL bundle and the theme CSS uses physical properties.

## Where catalogs live

```
locales/
  en/   admin.ftl  common.ftl  errors.ftl
  vi/   common.ftl  errors.ftl
```

**Transactional email copy is not here.** It lives in the `email_templates` table,
per `(key, locale)`, editable at `/admin/email-templates`, and falls back to
`EMAIL_TEMPLATE_DEFAULTS` in `ferum-domain/src/models/email_template.rs` for any
locale an admin has not overridden. It is the one user-facing surface a translator
cannot contribute to by editing a `.ftl` — that cost was accepted so the copy could
be edited without a deploy.

Every `.ftl` in a locale directory is merged into one bundle, so splitting by file is
an authoring convenience. **Key names are the namespace, not filenames.** Files are
read in sorted order so a duplicate key resolves identically on every machine.

`LOCALES_DIR` points at the root. If the configured path is not a directory the app
tries `./locales` then `../locales` and logs a WARN naming what it used; if none
exists, **startup fails**. That is deliberate: an earlier version warned and continued,
and shipped a forum whose navigation read `ui-home` / `ui-categories` with nothing
surfacing it.

Themes contribute catalogs from their own tree. Roots are loaded in ascending
precedence — core first, then themes — so a theme can override a core string as well
as add its own, the same direction the theme template chain resolves in.

## Key namespaces

They are not interchangeable. Using the wrong prefix fails silently.

| Prefix | Catalog | Used by | Count in `en` |
| --- | --- | --- | --- |
| `ui-` | `common.ftl` | server-rendered public and member templates, via `{{ t(k="ui-…") }}` | 454 |
| `js-` | `common.ftl` | client-side JavaScript, via `Ferum.t('js-…')` | 150 |
| `adm-` | `admin.ftl` | admin and moderator panel templates | 587 |
| `error-` | `errors.ftl` | API error messages | 128 |

- **`js-` is the only namespace reachable from JavaScript.** The server serialises a
  `js-`-scoped dictionary into `<meta name="ferum-i18n">` and `Ferum.t()` reads it.
  `Ferum.t('ui-something')` renders the raw key — it does not fall back and does not
  warn.
- **`error-` is the only place API error text lives.** `AppError` carries a machine
  code (e.g. `permission_denied`); the `translate_errors` middleware resolves
  `error-<code-kebab>` against this catalog on the way out. Never put user-facing prose
  into the Rust `AppError` construction — pass a code and add a catalog entry.
- **`adm-` ships English-only by decision.** The strings are extracted, so adding a
  language later is data-only, but `locales/vi/` has no `admin.ftl` and admin JavaScript
  is not required to route through `Ferum.t()`.
- A partial included from both an admin and a public page cannot use `adm-`, because
  the public page's catalog does not carry it.

## Rules when writing templates

- **Every user-facing string in a public or member template goes through
  `{{ t(k="ui-…") }}`** — including `placeholder`, `title`, `aria-label` and `alt`, not
  just text nodes.
- **Add a new key to every installed locale in the same change.** A key in `en` but not
  `vi` is an incomplete change; diff the key sets rather than checking that the page
  renders once in your test locale.
- Prefer reusing an existing key over minting a near-duplicate. `ui-cancel` exists —
  do not add `ui-close-dialog` for the same word.

Two test suites enforce parts of this. `backend/tests/web/src/template_keys.rs` asserts
that every `t()` key appearing in every template actually resolves — Tera does not fail
at parse time on a missing key, so nothing else would catch it.
`template_integrity.rs` exists because the bulk-extraction script corrupted templates
twice during the original migration.

## How a request gets its locale

`negotiate_locale` resolves, in order:

1. URL path prefix — `/vi/forum/t/slug`
2. query parameter
3. the `ferum_locale` cookie
4. `Accept-Language`
5. the **site default** — `site_config.default_locale`, read from the in-memory config
   cache. Any installed locale; falls back to the source locale when the value is
   absent or names a locale with no catalog installed, because honouring that would
   render every string on the page as a raw key. `startup.rs` WARNs on that case.

Site default and source locale are **different things**, and neither substitutes for
the other:

| | `Locale::DEFAULT_TAG` (`en`) | `site_config.default_locale` |
| --- | --- | --- |
| Is | the **source locale** — the language the `.ftl` catalogs are written in | the **site default** — what a visitor with no preference is served |
| Governs | message resolution (`fallback_chain`), `site_text` storage keys | negotiation, and which locale is served on unprefixed URLs |
| Configurable | no | yes, `/admin/languages` |

A resolution chain ending at the site default would render a raw key for every string
only the source catalog carries. Negotiation pinned to the source locale is the bug
that made `default_locale` inert for its whole existence: it was written by the
Languages page and read back by nothing else, so "set as default" changed nothing a
visitor could see.

The path prefix is **stripped from the URI before routing**, so every route is declared
once and a route added later works in every language automatically.

That stripping is why the locale middlewares wrap the router with `fallback_service`
rather than being added to it with `Router::layer`. `layer` attaches middleware to each
endpoint, which means matching has already happened by the time it runs — and
`/vi/forum` matches nothing, so it would 404 before the prefix was ever removed.

Locale is a cookie rather than `localStorage` (which is how the theme preference works)
because it is baked into server-rendered HTML: it has to travel *with* the request, not
be applied by script afterwards. Subpath URLs were chosen over a `Vary`-based scheme so
each language is a distinct crawlable URL and the guest cache key falls out of the URL.

### Changing language

| Who | How |
| --- | --- |
| Guest | `PUT /api/locale` — sets the cookie. Deliberately open to guests; they are the majority of readers and have no account to hold a preference. |
| Signed-in user | The same endpoint, plus `user_preferences.locale` in the database. Nullable, meaning "no explicit choice — negotiate". |

## Administration

`/admin/languages` lists installed locales with their coverage against the source
catalog, and toggles which are offered. It is gated by its own `admin.languages`
permission, separate from `admin.config`, so a translator can be given language access
without SMTP credentials.

`PATCH /api/admin/languages/{tag}` is the write endpoint. Two `site_config` keys back
it, and neither is seeded:

| Key | Absent means |
| --- | --- |
| `enabled_locales` | every installed locale is offered — which no explicit value can express |
| `default_locale` | the source locale |

The site default cannot be disabled (`cannot_disable_default_locale`), and setting it
implies enabling it. Both keys are written through `AppState::set_site_config`, which
updates the row **and** the in-memory cache — the cache is what `negotiate_locale`
reads, so a write that skipped it would take effect only on the next restart.

The locale served on unprefixed URLs is the site default, which is what `hreflang`
advertises: the template compares each alternate against the `default_locale` context
variable, never a literal.

### Canonical URLs

The site default is reachable **two** ways — unprefixed and under its own prefix, so
`/forum` and `/vi/forum` are the same page when `vi` is the default — and tracking
parameters make the count unbounded. `base.html` emits one `rel=canonical` naming the
unprefixed form for the site default and the prefixed form for every other language,
built from the *resolved* locale so it always describes the page being served.

`middleware::locale::canonical_query` decides what of the query survives into it:
`?page=N` for N > 1, and nothing else.

| | Why |
| --- | --- |
| `page` kept | a canonical of `/forum` on `/forum?page=3` tells a crawler page 3 duplicates page 1, so every thread appearing only later leaves the index |
| `page=1` dropped | it and the bare path are the same page; self-canonicalising both leaves the duplicate standing |
| `utm_*`, `sort`, `tag`, `lang` dropped | collapsing tracking parameters is what the tag is primarily for, a reordering of the same items is a duplicate, and `lang` restates what the URL prefix already carries |

`hreflang` alternates are built from the same `current_path`, so a paginated page
advertises the same page in every language. `tests/web/src/hreflang.rs` pins that the
canonical and the self-referential alternate agree — they are separate expressions,
which is how they would drift.

Not implemented: uploading a language pack through the admin UI, and a per-string
override editor for the `.ftl` catalogs. Adding a locale today means adding a
directory under `locales/` and restarting.

Email templates are the exception for *shipped* copy, and the shape a general
override editor would follow if it is ever built: a database table holding only what
an admin changed, resolved over `Locale::fallback_chain()`, with the shipped copy as
the fallback and "reset" implemented as deleting the row.

### Site copy the admin writes

The slogan and the tagline are not shipped copy — an admin types them, and they reach
visitors. Both are translatable, through `ferum_domain::site_text`.

Storage is the flat `site_config` key space, suffixed. `site_tagline` holds the copy
for `Locale::DEFAULT_TAG`; `site_tagline:vi` holds a Vietnamese translation and exists
only once someone types one. `site_ctx` resolves over `Locale::fallback_chain()`, so
`vi-VN` → `vi` → the bare key, and an untranslated language falls back rather than
rendering blank — which matters most for the tagline, since that is every page's
`<meta name="description">`.

The bare key is keyed on the **source** locale, not the site default. Keying it on the
site default would mean changing that setting silently reassigns which language the
bare row holds, orphaning a `:vi` row the moment `vi` became the default.

It is `site_config` rather than a table because resolution runs on **every page
render**, against the whole-table `HashMap` already in memory. A table would need
either a second cache with its own invalidation or a query on the render path.

| | Where |
| --- | --- |
| Which keys are translatable | `site_text::LOCALIZED_CONFIG_KEYS` |
| Editing | `/admin/settings` → Site Identity → Slogan & Tagline, one language sub-tab per **installed** locale |
| Write path | `PUT /api/admin/config`, same as any other setting |

A field per *installed* locale, not per *enabled* one: `negotiate_locale` resolves
against the installed roster, so a disabled locale can still be served from
`Accept-Language`.

Adding a third translatable key is one line in `LOCALIZED_CONFIG_KEYS` plus a
`{{ adm::copy_field(...) }}` call inside the language panes.

## Dates, numbers and time zones

Formatting is catalog-driven, not `strftime`.

Server-rendered timestamps are emitted in **UTC** inside
`<time data-rel datetime="…">`, and `ferum-utils.js` rewrites them in the browser. The
conversion happens client-side for three reasons: the server does not know a guest's
zone, and guests are the bulk of the audience; baking a per-user zone into HTML makes
every page user-specific and forfeits the guest edge cache; and a signed-in user's
stored `user_preferences.timezone` still wins where set, published in
`<meta name="ferum-tz">` and fed to every date helper by `Ferum.tz()`.

The `localdate` Tera filter renders **UTC** deliberately. It localises month names and
field order through the catalog; it does not convert zones. Its output is the fallback
for a reader without JavaScript, so it must always be paired with a `datetime=`
attribute the client can correct. Never use it bare.

## Out of scope

User-generated content. Threads, posts and product descriptions stay in the language
they were written in; nothing translates them.
